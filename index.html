Under the hood

WHAT GETS
STORED

Every MemoryRecord has a mandatory why_text field — enforced at the database level. This is the entire differentiator.

DecisionConfidence: HIGH
Stripe chosen over Braintree — idempotency
What

Replaced Braintree with Stripe as primary payment processor. Migration completed Dec 2023.

Why

Braintree had no idempotency key support on retries — double-charging customers on network failures. Stripe idempotency keys make retries provably safe. This was the core reason. Any retry logic added here MUST use idempotency keys.

github · arjun@fintech.co2023-12-04[payments, idempotency, critical]
Risk flagStatus: RESOLVED
Retry logic not implemented — pre-launch risk
What

PaymentService.charge() calls Stripe with no retry mechanism. Risk of double charge on timeout.

Why deferred

Shipping MVP for demo deadline. Must add before real transaction volume. If Stripe times out and frontend retries without idempotency key, customers will be double-charged — the exact scenario that caused the Braintree migration.

cli · priya@fintech.co2024-02-28[payments, retry, risk, pre-launch]
Bug / incidentConfidence: HIGH
PAY-287 — double charge incident, 3 customers
What

3 customers double-charged during AWS degradation. Stripe refunds issued manually. March 2, 2024.

Why it happened

Stripe call timed out. Mobile app retry fired with a new request. No idempotency key. Stripe processed both as separate charges. Root cause: open risk flag was never resolved before going live with real transactions.

jira PAY-287 · arjun@fintech.co2024-03-03[payments, bug, double-charge, post-mortem]
CommitConfidence: HIGH
PAY-391: exponential backoff + idempotency keys
What

Added tenacity retry decorator to PaymentService.charge(). Max 3 attempts, base 500ms, 2× multiplier, 8s max, jitter. Idempotency key = SHA256(payment_id + attempt_number).

Why

Closes risk flag from Feb 28. PAY-287 confirmed urgency. Using tenacity over manual loop for built-in jitter, per-exception retry conditions, and retry stats logging. Parameters from legal review (max 3) and Stripe rate limit tuning.

Cursor integration

ONE CONFIG
FILE.
THAT'S IT.

SWAPCORE connects to Cursor via MCP — the Model Context Protocol. Cursor calls SWAPCORE tools automatically before answering architecture questions. No plugin. No workflow change.

~/.cursor/mcp.json
// The only file you need to create.
// SWAPCORE works after this. Forever.

{
  "mcpServers": {
    "swapcore": {
      "command": "swapcore-mcp",
      "args": ["--project", "my-app"],
      "env": {
        "SWAPCORE_API_KEY": "sk-swapcore-..."
      }
    }
  }
}
Terminal — one-time setup
# 1. Install the SWAPCORE MCP server
npm install -g @swapcore/mcp

# 2. Initialise your repo (once per project)
cd your-repo && swapcore init \
  --project my-app \
  --github-repo org/repo

# Done. Cursor now has full SWAPCORE access.
# Every commit captured. Every question answered.
01
Cursor calls SWAPCORE automatically
When you ask an architecture or debugging question, Cursor's MCP client calls swapcore_get_context() before responding. You never trigger this manually — it just works.
02
Memory brief injected into system prompt
The top 8 relevant MemoryRecords are formatted and prepended to Cursor's system prompt. The AI reads 6 weeks of team decisions before answering. You just see a much better answer.
03
Git hook captures every commit silently
After swapcore init, a post-commit hook fires after every git push. Sends the commit to SWAPCORE. IntentInferrer infers why_text from your message, PR, and linked tickets. Zero manual effort.
04
Record key decisions in 30 seconds each
Two CLI commands at the end of a session. The reasoning you capture today will inform every developer — and every AI session — that touches this code in the future.
